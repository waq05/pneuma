## 一、patch config 的生命周期（问题 1）

以组合包 patch 写 `config: {foo: 1}`、插件 `apply(ctx, passed)` 为例：

| 阶段 | apply 收到 | 插件随即调 `resolvePluginConfig` | 依据 |
|---|---|---|---|
| 装机后首次挂载（`plugins.json` 无该条） | `{foo:1}` | `{foo:1}`（磁盘空） | `plugin-loader.ts:1606`、`plugin-registry.ts:391` |
| 挂载过、磁盘已有该条 `{foo:0}` | `{foo:1}`（整块替换） | **`{foo:0}`**：同一函数里优先级翻转 | 实测 D |
| 用户改设置 `foo=9` | — | `{foo:9}`；只在 apply 读一次的插件永远读不到 9 | `plugin-registry.ts:362-379` |
| 重启 | `{foo:1}`（整块替换磁盘） | `{foo:9}` | 实测 A/D |
| 界面点一次「停用→启用」 | **磁盘那份 `{foo:9}`/`{}`，patch 的 foo 丢了** | 同左 | `plugin-loader.ts:927`，实测 C |
| 代码热更重挂 | `{foo:1}`（沿用 `mountDetails.options`） | `{foo:9}` | `plugin-loader.ts:754/780` |

答：**不是「第一次保存后被顶掉」，是从第一次读起磁盘就压过 patch**——`resolvePluginConfig` 写成 `{...passed, ...fromDisk}`（`plugin-registry.ts:391`），磁盘逐键覆盖 patch，patch 独有的键才留得下来。挂载侧却是「整块替换、不深合并」（`plugin-loader.ts:1606`），磁盘独有的键在 mount 那一刻全丢（实测 patch 在 `apply` 里看不到磁盘的 `disk` 键）。挂载与运行期对同一份数据给出相反优先级，是本次修复新引入的口径分裂。

## 二、写盘次数（问题 2）

|---|---|---|
| 界面/TUI `ui.setPluginEnabled` | 宿主行（组合包行、外部单文件）→ `setPluginEnabledHot` | 1（启用成功）/1（停用）/1（启用失败，`disableSilently` 回滚） |

## 三、判定等价性（问题 3）

同一份 `plugins.json` 逐例比对（源码探针；旧语义用 `entries.find(e => e.file === f)?.disabled ?? false` 复刻）：

| 用例 | 旧判定（启用?） | 新 `isPluginEnabled` | 结论 |
|---|---|---|---|
| 精确键 开/关 | 开/关 | 开/关 | 等价 |
| 旧键别名（行 id `bundle-row`，条目只记 `legacy-name.js`） | 开 | **关** | 有意修 |
| `defaultDisabled` 且无条目 | 开 | **关** | 有意修 |
| 大小写（`Case.js` / `case.js`） | 关/开 | 关/开 | 等价（都区分大小写） |
| `.js` 后缀（`withsuffix.js` / `withsuffix`） | 关/开 | 关/开 | 等价 |
| 目录名 vs 文件名（catalog 有 `pkg-a/a`，问 `a.js`） | 开 | 开 | 等价；这种形状错位两边都判不出 |

「文件名 `a.js`、catalog 叫 `pkg-a/a` 会不会恒判为启用」：`mountAllExternalPlugins` 只遍历 `~/.dsc/plugins/*.js` 与 `extraPaths` 的 basename（`plugin-loader.ts:955-963`），外部文件挂载时 catalog 键就是文件名（`:564/:571`），两条路字符串一致，常规流程不会错位。只有「同一物理文件既作 extraPath、又作组合包行」时，组合包行的 `pkg-a/a` 条目管不住 `a.js` 那一趟——旧代码同样管不住，不是本次回归。

## 五、真问题

1. **热开关丢掉 patch config** — `core/plugin-loader.ts:927`（重挂不传 `rowOptions`）对 `:1606`（首次挂载传）。现象：实测「停用→启用」后 `apply` 收到磁盘那份 `{foo:0,disk:"only"}`，patch 的 `{foo:1}` 消失。触发：任何带 `config:` 的组合包行，用户拨一次开关。建议：`setPluginEnabledHot` 取 `mountDetailsOf(root).get(file)?.options` 传回去（`unmountExternalPlugin` 不清理 details，见 `plugin-loader.ts:894-906`，改动很小）。置信度：高（探针直接复现）。
2. **挂载与运行期优先级相反** — `plugin-loader.ts:1606`（整块替换）对 `plugin-registry.ts:391`（磁盘逐键覆盖）。现象：组合包默认值在 `apply` 里生效，插件一调 `resolvePluginConfig` 就被用户旧设置顶掉；只在 `apply` 读一次的插件则永远读不到用户新设置。触发：组合包行带 `config:` 且 `plugins.json` 有同名键。建议：`hostGiven` 保持整块替换（llm/session 磁盘上本就没有），`rowGiven` 改走 `resolvePluginConfig(rowId, rowGiven)`；或明确「patch > 磁盘」，那就把合并顺序改成 passed 覆盖磁盘，并放弃「保存即生效」。置信度：高（代码 + 实测 D）。
3. **`registerBuiltinMount` 没有调用方** — `plugin-loader.ts:267` 只有定义与文档引用，全仓无调用。现象：内置分支 `:536-555`（P0-2 改的 `rowOptions.config ?? getPluginConfig(base)`）在现网走不到，内置行全走外部分支。触发：无需触发，现状如此。建议：要么补调用方，要么在结论里注明这条改动当前是死路径（不影响正确性）。置信度：高（全仓 grep）。
4. **装插件绕过开关判定** — `packages/plugin-manager/index.ts:91/134` 复制/下载后直接 `mountExternalPlugin`，不问 `isPluginEnabled`，也不写 `enabled=true`。现象：用户停用过的 `foo.js` 再装一次同名文件会被挂上，`plugins.json` 仍是停用——插件中心显示「关」、实际在跑，正是 P0-4 想消掉的分歧。触发：先停用，再 `plugin_manager install` 同名文件。建议：install 成功后走 `setPluginEnabledHot(file, true)`，或挂载前判一次开关。置信度：中高（读码，未实跑）。
5. **`plugin_manager` 对内核行的报错文案错** — `packages/plugin-manager/index.ts:76` 不判 `canTogglePlugin`，`builtinMounts` 又是空的（同第 3 条），于是 enable 一个内核行会返回「找不到插件文件 xxx（检查 ~/.dsc/plugins/）」，真因是「这一档不能停用」。0 写盘、无数据风险，只是误导。置信度：高（读码）。
