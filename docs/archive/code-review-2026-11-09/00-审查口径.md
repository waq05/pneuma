# 2026-11-09 代码规范与架构审查 · 统一口径

> 状态：已归档（2026-11-17）：2026-11-09 一次性审查报告；14 条 P0 已全部修复（见同目录 FIXES.md）。

## 背景

Pneuma（numa）从单体内核迁移到「一个能力一个包」的插件模型，迁移途中留下了新旧两条路径。
用户反馈：旧逻辑与新逻辑冲突，重复实现多，耦合重，已经影响继续开发。本轮只审查、不改代码。

分支 `feat/pluginization`，工作区有 30 个文件在途改动。**一律按工作区现状审查**，
在报告里注明「该文件有未提交改动」。

## 只读纪律

- 禁止修改、创建、删除任何源码或配置。
- 唯一允许写入的位置：本批次报告文件 `docs/code-review/2026-11-09/NN-*.md`。
- 禁止跑 `pnpm install` / `build` / `typecheck` / 测试；只做静态阅读与检索。
- 可以用 `read`、`grep`、`glob`，必要时用只读的 `pwsh`（`Select-String`、`Get-Content`）。

## 五类靶子（按优先级）

1. **旧/新双路径**：同一能力存在两套实现或两条调用链。典型是 `src/core/<x>.ts` 一行转发到
   `src/packages/<pkg>/<x>.ts`，而调用方有的走旧路径 `@pneuma/runtime/core/x.js`、有的走
   新路径 `@pneuma/<pkg>`。要判断哪条是活的、哪条只剩测试或没人用。
2. **重复逻辑**：同一段判断/格式化/状态机在两个以上文件各写一遍（含 UI 与 TUI 各一份、
   宿主与渲染层各一份）。给出两份实现的位置与差异。
3. **耦合与分层违规**：core 反向依赖 packages；包与包直接 import 对方内部文件而不走契约；
   UI 包 import Node 内置模块；`ctx.get('某服务')` 绕过契约直接摸别的包内部状态；
   import 环。
4. **上帝模块**：单文件超过 800 行或明显承担三种以上职责；一个 `apply()` 里塞了整条业务链。
5. **状态与事件重复**：同一状态在多处各存一份（快照、localStorage、jsonl、内存缓存），
   同一事件被多个包各自解释；失效逻辑分散导致「改了 A 忘了 B」。

## 每条发现必须长这样

```md
### [P0|P1|P2] 一句话结论
- 位置：`src/packages/x/index.ts:123`（可多个）
- 现象：发生了什么，为什么是问题。
- 证据：摘 1–3 行原文（带行号），不要转述。
- 影响：继续开发会踩什么坑；不写抽象形容词。
- 建议：删除 / 合并到哪 / 抽成哪个模块 / 改成走哪个契约；给一个可执行动作。
- 置信度：高（已核对全部引用）/ 中（抽样）/ 低（推测，需复核）。
```

严重度口径：

- **P0**：已经在制造 bug 或必然导致改 A 坏 B（双写、双状态、循环依赖、启动顺序靠巧合）。
- **P1**：显著增加改动成本，下一次需求大概率踩到（重复实现、上帝模块、契约外的直接依赖）。
- **P2**：可读性/一致性/死代码，清理收益明确但不紧急。

## 纪律

- 不把「注释多」「中文注释」「文件大但单一职责」直接当问题。
- 不把「刻意的兼容层」直接判死：先查引用；查不到就写「疑似死代码，待核实动态引用」。
- 不臆造行号。报告里的每个 `文件:行号` 必须是你真读到的。
- 不确定就写进「待核实」，不要凑数。
