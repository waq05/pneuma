## 二、真问题

**1（P1，实测）队友会话解析不到，`todo_write` / `goal` 写进用户正看着的会话。**
`src/packages/todo/index.ts:145`、`src/packages/goal/index.ts:96` 都用 `ctx.agent.sessionById(sessionId) ?? sessionFor(path) ?? ctx.session.current()`；
而 `src/packages/agent/index.ts:327-335` 的 `agents` 表只在 `attach` 时登记（`:227`），队友是 `src/packages/subagent/index.ts:642/646` 直接 `Session.create/load` 出来的，**不进这张表**。
触发：任何队友（`badge.tools === null` 或白名单含 `todo_write`，见 `subagent/index.ts:447-469`）调一次 `todo_write` 或 `goal`。
影响：状态写进用户眼前那条 jsonl，并把用户自己的清单/目标顶掉——P0-7 的原始症状原样存在。
实测：`node tmp-repro/probe-p0-679.mjs` 的 [A] 4 条断言全 FAIL（队友收到 0 条写入，被看会话收到 todos 与 goal 各一条）。
建议：会话解析收成一处（例如让 subagent 把自己的 Session 注册进 agent 名册，或加 `ctx.session.resolve(runCtx)` 同时问 `subagent`），别再让三个插件各写一遍 `sessionById ?? current`。置信度：高。

**2（P1，实测）计划僵尸卡：答不掉、也挡到永久。**
`src/packages/plan/index.ts:143-150` 的 `answerPlan` 只认 `cardOfCurrent()`（活卡），`restored`（`:62`）走不到任何收尾路径；`finish()`（`:90-129`）也不清 `restored`。`restored` 又被写进 `waiting` 登记（`:160`），且计划卡是三类卡里**唯一没有超时**的。
触发：上次进程崩在「已提交计划、未获批」时（jsonl 里留下 `decision: 'pending'`）。
影响：点批准/拒绝是空操作，评审卡在界面上去不掉；`anyFor(该会话)` 恒为真 → 这条会话的目标自动续跑永久停摆，重启也还在（状态条目没被改写）。
实测：`node tmp-repro/probe-plan-zombie.mjs` [1] 「点批准后僵尸卡消失 / anyFor 变假」FAIL；[2] 「同一会话交新计划并批准后僵尸仍挡」FAIL。
建议：`answerPlan` 在无活卡时把 `restored` 按会话写一条终结状态并清掉；`finish()` 里顺手清同会话的 `restored`。置信度：高（行为实测）。

**3（P1，读码）5 个次级审批入口没带会话，卡片归属落到「当前查看的会话」。**
`src/packages/hooks/index.ts:423-427`（钩子 `ask` 卡，`input.sessionId` 就在手边却没用）、`src/packages/memory/index.ts:342-350`、`src/packages/self-improve/index.ts:365-373`、`src/packages/mcp/index.ts:490-498`、`src/packages/desktop-dock/index.ts:320-323`。
`approval` 侧 `sidOf = request.sessionId ?? ctx.session.current().meta.id`（`approval/index.ts:795`，卡片在 `:954-963` 用的是它）。
触发：后台会话的工具命中 `ask` 钩子，或后台会话调 `memory` / `skill_write`。
影响：这张卡被记在用户正看着的会话名下 → 那条会话的目标仍被钉死（P0-6 症状复现）；同时审计与 `allow-session` 授权（`approval/index.ts:1481-1483`）也记错会话。主链（`approval/index.ts:1511-1512`）是对的，只有这几处漏。
建议：这五处补 `sessionId: input.sessionId / scope.sessionId`。置信度：高（代码路径清楚，未跑端到端）。

**4（P2，读码）schedule 的闸还是超集，一条卡能拖住整批。**
`src/packages/schedule/index.ts:222-228` 取「所有启用任务的目标会话 + 当前会话」求或；`core/schedule/runner.ts:280/386/467/537` 是 `waiting: () => boolean`，一次判定管一整批（含手动 `fireNow`）。
触发的例子：任务 A 投给会话 X、任务 B 投给会话 Y；Y 挂着审批卡 → A 的投递也推迟。
影响：比修前好（不再被「完全无关的会话」挡住），但「一个卡挡住一批」没变。
建议：把 dep 签名改成 `(sessionId: string) => boolean`，逐条任务判自己要投的那条会话。置信度：高。

**5（P2，读码）压缩时「原样带过去」的清单/目标还是取当前查看的会话。**
`compact/index.ts:215-221` 的 `carry()` 不带会话，`:305-325` 的 `check(signal, target)` 却是按目标会话压的，`src/packages/todo/index.ts:200`、`src/packages/goal/index.ts:234-238` 两个 carry 贡献者都调 `store()`（= 当前查看会话）。
触发：后台 agent 触达压缩线（`agent/index.ts:168` 每个 agent 都挂 `compact.check`）。
影响：后台会话的压缩摘要里被塞进用户眼前那条会话的清单与目标，它自己的被丢掉——P0-7 的同一根因，只是走提示词而不是写盘。
建议：`registerCarry((session) => string)` 带上目标会话。置信度：高（代码形状确定，未跑压缩端到端）。

**6（P2）`anyFor` 在契约里不存在，老式登记仍然挡住所有会话。**
`src/services/types.ts:505-512` 还是 `register(id, pending: () => boolean)` + `any`；`anyFor` 靠 `src/packages/waiting/index.ts:26-31` 的 `declare module` 补，只对本仓编译有效，第三方插件包看不到；
而 `waiting/index.ts:52-61` 对老式 `() => boolean` 的语义是「对任何会话都算在等」（探针 `waiting-session-scope-check.mjs` [5] 还把它钉成期望）。
影响：本仓三处登记都带了 owner，现网无残留；但任何外部插件按老契约登记一次，P0-6 就退回「一张卡挡住所有会话」。另注：修后 `waiting.any` **已无生产消费者**（只有测试与 README），「`any` 留给界面」这句自述目前不成立。
建议：把 `anyFor` 与 `(owner?: string) => boolean` 写进契约；文件头注释里写明「老式登记 = 挡全部」是已知取舍。置信度：高。

**7（P2，实测）`grep` 的读禁判定每个文件多一次 `realpathSync`，实测并不便宜。**
`src/core/path-policy.ts:190-196` + `:134-149`（每次判定都跟一遍真实路径）。
本机实测（`node tmp-repro/probe-perf.mjs`，1098 个真文件）：`realpathSync.native` 302.9 µs/次、`statSync` 133.5 µs、`readFileSync` 263.9 µs。即单文件开销从约 400 µs 涨到约 700 µs（+75%）；5 万个文件多约 15 秒。
关键点：`grep` 的 `walkFiles` 只收 `entry.isFile()`（`search-tools.ts:304`），**软链根本进不来**，所以这一路的 realpath 是纯亏。
建议：给 `grep` 用「只判字面路径」的变体，或按目录缓存 realpath（同目录复用）。置信度：高（数字实测，量级随机器变）。

**8（P2）文档没跟上，而且有三份 README 现在写的是旧行为。**
`src/packages/waiting/README.md:8`、`src/packages/goal/README.md:10`、`src/packages/schedule/README.md:11`、`src/core/schedule/runner.ts:21` 都还写 `ctx.waiting.any`；`docs/development-log.md` / `docs/development.md` 里**没有这三条的记录**（`git diff` 里搜不到 P0-6/7/9）。按工作区规则 11，这一批缺文档。置信度：高。

**9（P2，取舍）误伤确认：`~/.dsc/plugins.json` 现在读不了，也改不了。**
`src/core/path-policy.ts:220-227` 新增读禁；`src/core/tools/fs-tools.ts:230` 的 `edit` 也过它。模型排障时既读不到插件注册表、也不能用 edit 改它（改要走设置页或 `numa plugin` CLI——这两条路都没被挡，功能没断，只是模型不好自查）。置信度：高。

## 三、查过并判定没问题的

- 三处登记的会话键确实是同一套：approval 用 `sidOf(request)`（`approval/index.ts:894`）→ `card.sessionId`（`:960`）；ask 用解析后的 `session.meta.id`（`ask/index.ts:191`）；plan 用 `proposed.meta.id`（`plan/index.ts:130`）。`goal`/`schedule` 查询传的也是 `meta.id`（`goal/index.ts:163`、`schedule/index.ts:227`），**没有 `sessionPath`/`meta.id` 混用**。
- 「旧卡没有 `sessionId` 字段会被永久漏判」不成立：ask/plan 的 `pendings` 只在内存里、创建时必带；plan 的僵尸卡归属由会话状态推导（`plan/index.ts:64`），不依赖存过的字段。
- ask 卡有 `waitMs`、审批卡有 `timeoutMs`，都能自解；**只有计划卡没有超时**（这就是问题 2 的放大器）。
- `grep` 的绕行实测都挡住：`.env` / `.ENV` / `*.pem` 正文不出现、`已跳过 N 个受保护文件` 有说明、单文件 `.env` 与 `.ENV` 整条报错、`sub` 起搜不读父目录、junction 指回父目录也不漏（`tmp-repro/probe-p0-679.mjs` [C]，`scripts/grep-read-denylist-check.mjs` 19/0）。
- `edit` 的「读禁先判」放在 `writeHardBlockReason` 之前（`fs-tools.ts:230-233`），且被拒后文件未改（探针 [6]）。
- 「`todo_write` 原来根本不落盘」属实：`git show 752badb:src/packages/todo/index.ts` 里 `appendState` 只在 `writeTodos` 服务方法与 `clearTodos` 上，工具没调；旧 lib 的 e2e jsonl 里也只有 `clearTodos` 那一条 `todos` state。
- 会话归属的 A/B 用例（B 挂卡、A 续跑）用真 `waiting` + 与源码同形的登记闭包跑通：`todo-session-scope-check.mjs` [5]、`waiting-session-scope-check.mjs` [2][3] 全 green。
