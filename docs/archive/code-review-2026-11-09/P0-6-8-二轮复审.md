## 一、结论：**有条件可收**

- P0-6 的僵尸卡收口是真修：`settleRestored`（`plan/index.ts:88-112`）、`finish` 顺带清、`waiting` 按会话登记（`:203-210`）三条闭合，探针 24/0；活卡全程不写 `pending` 状态，所以不会把活卡误判成僵尸（问题 5）。
- P0-8 的机制对（gate 入口一处改写、认人标记随 `facts` 下发、owner 派活时固化），但它只把身份换成 **id/path 字符串**；`sandbox`、`mode`、审批策略层还要靠 `agent.sessionById/sessionFor` 反查，反查落空就回落 `ctx.session.current()`——也就是 P0-8 的原症状。后台会话派队友、或用户切过 3 条以上会话后，这条回落会重新打开（问题 1/3、真问题 1）。
- 另有四处次生问题（hooks ask 绕过队友工牌、LSP 诊断记错会话、MCP 卡按建连会话归属、僵尸卡先清内存后写盘）。

**收的条件**：给「解析不到归属」补一条兜底（按路径只读加载会话，或直接按拒），别回落成当前查看的会话；hooks ask 与队友工牌的关系要定口径。

## 二、11 个问题

**1. `resolveSession` 会不会解析到错误会话？并发会不会串？**
不会串。解析器按插件 id 只一份（`core/tool-guards.ts:111,130-135`），subagent 那份每次现扫 `teammates` 按会话 id 精确比对（`subagent/index.ts:538-551`），并发队友各查各的。防环（`seen`，`:145,152`）与「认不出原样返回同一个对象」（`:143,162`）都成立。
没找到「解析到错误会话」的路径，但有「解析不到 → 退化成错会话」的路径：owner 会话已从 `agents` 名册消失时，下游 `sessionOf` 回落当前查看会话（真问题 1）。窄边界：`teammateOf` 先认名字再认 id（`subagent/index.ts:554-561`），同名队友被挤出后又建一个时，在飞调用会认成新的那位（map 键是名字，`:824`），只在旧队友仍留有在飞调用时成立，概率极低。

**2. 哪些守卫依赖「sessionId 是真实执行者」？**
按 id/path 做权限判定的三位是设计内的：`sandbox`（`sandbox/index.ts:285-286` 取档、`:213` 按 path 取「本会话允许」的可写根）、`mode`（`mode/index.ts:96-103`）、`approval`（`approval/index.ts:1499-1516` 记账与卡归属）。改写后拿到父会话，是要的效果。
被改坏一位：`lsp-observe`（`lsp/index.ts:431-433` 存 `input.sessionId`，观察者 `:487-498` 按它写 `pendingDiagnostics`）——队友的写后诊断记到父会话，队友自己收不到（真问题 3）。
两位不受改写影响：`spill` 观察者签名里没有会话，只读 `ctx.session.current()`（`spill/index.ts:70`），队友长输出落进「正看着的会话」目录；`hooks` 规则是全局 `hooks.json`、不按会话过滤（`hooks/index.ts:276-280`），只用 `input.sessionPath` 决定通知写谁（`:413`），改写后写父会话，符合预期。

**3. 解析表会残留或提前失效吗？构造「一次性队友出队后仍有在飞 PTC 调用」**
表不会残留：按 id 注册、`ctx.effect` 收回，退订前比对 `get(id) === resolve`（`tool-guards.ts:130-135`），重载不会误删新的那份。
「失效」是设计好的：每次现扫 `teammates`，一出队（`subagent/index.ts:448` 一次性收工、`:1253-1262` 挤出名单、`:1025` 名册移除）就认不出。
构造场景：`await sdk.x()` 这条路**撞不上**——PTC 的 `deadline.hold` 是「停表 + await」（`ptc/index.ts:98-111`），工具结果返回时 gate 早走完。只剩两种能撞：脚本里没 await 的调用、工具本体起后台任务再回头调 gate。后果两级：`teammateOf` 认不出 → 29 号 defer → 30 号用队友会话 id/path 登记卡，而 `pendingView`/`answer` 只认当前查看会话的 path（`approval/index.ts:818-824,1435-1441`），这张卡界面上看不见，队友等满 300 秒（`:59`）按拒；同一次调用沙箱按当前会话给档。会话关闭：subagent 没有 `dsc/session-open/close` 监听（全仓也没有 session-close 事件），父会话收摊（`agent/index.ts:179-184,190-198`）不打断队友，但解析出的 owner 就不在名册里了。

**4. hooks ask 传「已解析成父会话」的 sessionId 符合预期吗？**
归属符合：卡落派活会话，档位、`allow-session` 记账、可见性都对（`hooks/index.ts:425-436`）。代价是队友身份丢了：卡面只有工具名（`:427`），用户看不出是队友在要；且这一问在 order 20 就 `pass`（`:443`），order 29 的队友审批被跳过（`tool-guards.ts:183`），于是「工牌不许请求授权」「后台队友不许问」（`subagent/index.ts:635-637`）在钩子这条路上失效。

**5. 活卡挂起期间会不会写 pending 状态？会不会被当僵尸清掉？**
不会。`plan` 状态只有两个写入点，都只写终态：`finish`（`plan/index.ts:133`）与 `settleRestored`（`:95`）；`propose` 全程不落 pending（`:119-178` 只有 emit）。正常退出时活卡由 `finish('rejected', true)` 落终态（`:280-283`），所以僵尸只来自崩溃。`answerPlan` 也先认活卡（`:188-193`），有活卡就轮不到 `settleRestored`。

**6. 用户正要点僵尸卡，另一个入口交了新计划，会点空吗？**
不会点空，会**批到没读过的计划**。`propose` 先 `settleRestored('rejected', true)` 作废旧卡（`plan/index.ts:124`），紧接着（同一个同步块、中间无 await）注册新卡（`:174`）。界面 `answerPlan(decision, feedback)` 不带卡 id（`services/types.ts:396`、`ui-prompt/ui/ui.tsx:660`），按「此刻的卡」执行。于是这一刻之后到达的点击批/拒的是新计划：用户刚看着的卡换了内容还没读，模型已经按新方案开工。触发：重启后僵尸卡还挂着、用户正看它，同时模型（或被唤醒的后台回合）为同一会话又交一份计划。概率低。

**7. `finish` 清 `restored` 会不会误清别的会话？**
不会。两处都比对 `restoredSessionId === proposed.meta.id`（`plan/index.ts:124,136`），而 `restoredSessionId` 只在启动（`:64`）与 `dsc/session-open`（`:275`）写成当前查看会话的 id。同会话的落点也对：`plan` 只有一个状态槽，新卡 `appendState`（`:133`）本来就盖掉旧卡那条 pending。

**8. `restored` 单槽、后台僵尸卡不登记，会不会让目标续跑永久停摆？**
不会，「切回时可恢复」成立。`restored` 只跟随当前查看会话（`:62-64,274-275`）：后台会话 B 的僵尸卡本来就看不见也答不了，此时 `anyFor(B)` 为假、续跑照常；切到 B 时 `session-open` 重新读出 pending → `anyFor(B)` 为真 → 挡到用户批/拒或交新计划为止，两个动作都写终态（`:95,133`）。取舍是「没人能答就不挡」，以及 `waiting.any`（全进程口径）会被当前会话的僵尸卡拉真——`any` 目前没有生产消费者。

**9. 契约放宽后还有谁依赖旧签名？`anyFor` 有没有传 undefined？**
实现只有 `waiting/index.ts:49-70` 一处；三处登记全带 owner（`approval/index.ts:1529-1533`、`ask/index.ts:243-245`、`plan/index.ts:203-210`）。`anyFor` 调用方只有 `goal/index.ts:188`（`session.meta.id`）与 `schedule/index.ts:222`（空串先短路成 false），没有传 undefined 的。`any`/`ids` 已无生产消费者；`schedule/index.ts:11` 的注释仍写「投递前问 `ctx.waiting.any`」，与 `:222` 不符。

**10. 四处补的会话是「发起调用的会话」还是「连接建立时的会话」？**
memory（`memory/index.ts:337-352`）、self-improve（`self-improve/index.ts:646` 传 `scope`）、desktop-dock（`desktop-dock/index.ts:320-329` 取点文件面板那一刻的查看会话，与它算 `cwd` 的口径同一条）都是发起方。MCP 是**建连时**的：`const owner = sessionIdentity()` 在 `connect()` 里算一次（`mcp/index.ts:487`），`onElicitation` 只用这份快照（`:511`）——长连接 + 用户切会话后，卡记在旧会话名下（真问题 4）。

**11. 四条探针**：见第四节，全部源码口径、全绿。另：`node scripts/check-p0.mjs --list` 的清单里**没有** `plan-zombie-card-check` 与 `teammate-session-alias-check`（本轮两个修复的定点探针），这条手动总闸漏了本轮。

## 三、真问题

1. **P1｜归属只换成 id/path，owner 不在名册时仍回落「正看着的会话」**（读码）
   `subagent/index.ts:538-551`（只给 id/path）→ `sandbox/index.ts:175-184`、`approval/index.ts:719-725`、`mode/index.ts:96-103` 都靠 `agent.sessionById/sessionFor`，而两者只查 `agents`（`agent/index.ts:327-335`）。
   触发：派活会话的 agent 被收摊——后台/定时会话回合结束即收摊（`agent/index.ts:179-184` 的 `onIdle`，只要不是当前查看的就 `disposeAgent`），或用户切过 3 条以上会话把它挤出空闲名单（`:218-222`，`IDLE_KEEP=3`）。
   后果：队友后续每次调用的沙箱档、权限档、审批策略都按「用户正看着的会话」算；那条是完全访问档时 teammate 的写不再受围栏（P0-8 原症状）。`teammate-mode`（9）反而没事，它直接握 `ownerSession` 对象（`subagent/index.ts:605`）。
   建议：解析器带 `Session` 对象，或三处 `sessionOf` 在 id/path 落空时按路径只读加载（照 `todo/index.ts:160-167`），并禁止回落 `current()`；做不到就按拒。置信度：高（链完整，未端到端跑）。

2. **P2｜队友出队后在飞调用丢归属：卡看不见 + 空等 300 秒**（读码）
   `subagent/index.ts:448,1025,1261` + `approval/index.ts:818-824,953`。触发：一次性队友出队/被挤/被移除后，脚本里没 await 的调用到达 `gate`。后果见问题 3。建议：出队时保留一段带 TTL 的退役映射。置信度：中（机制确定，触发面窄）。

3. **P2｜队友的写后 LSP 诊断改挂父会话**（读码）
   `lsp/index.ts:431-433` 记 `input.sessionId`，`:487-498` 按它 `pendingDiagnostics.set`，投影 `:209-221` 按请求所属会话取。改写后记到父会话：队友收不到自己写入的诊断（无法自我纠正），父会话下一轮凭空多一段没写过文件的诊断。建议：`facts` 里同时带原始 `teammateSessionId`。置信度：高。

4. **P2｜MCP elicitation 卡按建连会话归属**（读码）
   `mcp/index.ts:468-472,487,511`，`ELICITATION_TIMEOUT_MS=600_000`（`:786`）。触发：启动建连时看的是 A，切到 B 后用 MCP 工具、server 反向确认。后果：卡登记在 A 名下，B 的视图看不见也不会有人答，10 分钟后 abort 使卡按拒收场 → server 收到 decline。比修前（按「此刻查看」）好，但「发起这次调用的会话」仍拿不到。建议：把发起调用的 sessionId 随工具调用带进 elicitation，别用连接快照。置信度：中高（未起真 server）。

5. **P2｜hooks ask 绕过队友工牌上限**（读码）
   `hooks/index.ts:425-443`：20 号守卫自己问人、答完 `pass`，29 号队友审批（`subagent/index.ts:629-665`）被跳过。`approval: forbid` 或 `background: true` 的队友本来「不许请求授权」（`:635-637`），经钩子能弹卡，卡面也不署队友名。建议：ask 前先问 `canAsk`，或至少卡面写「队友 X」。置信度：高。

6. **P3｜僵尸卡先清内存后写盘**（读码）
   `plan/index.ts:93-95`：`restored = null` 在 `appendState` 之前。写盘抛错时内存已空、磁盘仍 pending，下次重启僵尸卡回来；而这次点击已经切了模式（`:103`）并写了审计（`:104-110`）。建议：先写盘再清内存。置信度：高（异常路径）。

7. **P3｜文档与总闸没跟上**
   `docs/development-log.md`、`docs/development.md` 的新增段落讲的是预览页签与运行记录，搜不到本轮 P0-6/P0-8 的改动（`git diff 752badb -- docs/development-log.md`）；`scripts/check-p0.mjs` 清单缺上述两条探针。
