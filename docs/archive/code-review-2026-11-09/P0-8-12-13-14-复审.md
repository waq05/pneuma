## 二、12 个问题的回答

**P0-8-1 队友是否吃到主链的全部守卫**：是。共享链按 order 排下来是 `computer-use-stop` 4 → `approval-floor` 5 → `lsp-observe` 7 → `sandbox` 8 → `teammate-mode` 9 → `mode` 10 → `browser` 20 / `hooks` 20 → `file-review` 25 / `lifecycle-hooks` 25 → `self-improve` 29 / `teammate-approval` 29 → `approval` 30；结果加工者是 `approval`(遮红) 10 → `hooks` 40 → `lifecycle-hooks` 45 → `lsp` 46 → `spill` 50。适配器只改 `sessionId`/`sessionPath` 并加 `teammate` 标记，其余字段与 `observe` 原样转给 `ctx.guards`（`subagent/index.ts:534-546`），所以队友拿到的是同一批对象。`gate()` 的短路语义（`tool-guards.ts:103-117`）没变，`pass` 会跳过后面所有守卫——这对队友的风险主要落在免打扰档，与主会话同语义，不是本次引入。
另外两点同 order 的细节：`self-improve` 29 排在 `teammate-approval` 29 之前（按 id 字典序，`tool-guards.ts:70-72`），它对 `skill_write` 返回 `pass`（`self-improve/index.ts:700-704`），于是队友调 `skill_write` 会跳过 29 号队友审批卡，回到「工具自带卡」那条既有设计。

**P0-8-2 29 在 30 之前是否让主审批的规则失效**：不会。29 的 `approve()` 调的就是同一个 `ctx.approval.decide`（`subagent/index.ts:597-609`），因此已授权规则（`approval/index.ts:1267-1276`）、地板白名单（1282-1288）、权限档自动放行、AI 复核全都在 29 内部照常生效。与 30 的真实差别只有三处：工牌上限与后台不许问（`subagent:593-595`）、卡面署名前缀（599）、授权归属改到父会话（605-606）。反过来「29 返回 defer 时 30 会不会按父会话档放行」：29 只在 `risk==='read'`（`tool-guards.ts:149`，30 同样 defer）或 `teammateOf()` 找不到人时 defer（`subagent:619`）。后一种发生在队友已从 `teammates` 表里消失的窗口——此时 30 拿到的是已改写好的父会话归属，档位是对的，但工牌上限与署名被绕过；窗口极窄（`settle` 只在回合结束后删一次性队友，`subagent:440`），判定为**不构成安全回退**，只是注释里「fail closed」那句在这条路径上不成立（真正 fail closed 的 `return false` 在 `:592` 已被外层 defer 挡在前面，不可达）。

**P0-8-3 嵌套队友、父队友已出队**：确实会停在中间层。`ownerSession` 沿 `teammates` Map 往上找（`subagent:499-509`），父队友一旦被删（一次性收工 `:440`、被 `MAX_LISTED_FINISHED` 挤出 `:1218`），循环第一轮就 `break`，返回中间层那条队友会话。后果两条：(a) 沙箱/模式用 `sessionById` / `sessionFor` 都找不到它（队友会话不在 `agent` 常驻表里），回落成 `ctx.session.current()`——即用户此刻看着的那条会话的档位（`sandbox/index.ts:175-184`）；(b) 审批卡按中间层会话的 `sessionPath` 登记，`pendingView()` 只返回「当前查看会话」的卡（`approval/index.ts:818-824`、`:1435-1441`），这张卡在界面上**看不见**，队友要干等到 300 秒超时（`approval/index.ts:59`）。触发条件：`maxDepth` 调到 2（默认 1，`subagent:104`，默认下嵌套派活直接被 `:1193-1195` 挡掉）且父队友是一次性/被挤出。

**P0-8-4 run_code / PTC 是否绕过适配器**：是，算没修干净。`ptc/index.ts:262-271` 直接把 `sessionId: session.id` / `sessionPath: session.path`（就是队友自己的会话，来自 `:391-395` 与循环的 `this.session`）交给 `ctx.guards.gate`。两位队友守卫靠 sessionId 反查（`subagent:512-519`）还能认人，所以模式与审批对；但 order 8 的沙箱在 9 之前跑，它拿到的是队友会话 → 两级查表都落空 → 回落成用户正看着的那条会话的沙箱档。用户切到「完全访问」档的会话时，队友脚本里的写操作就免掉围栏。

**P0-8-5 队友的 hooks `ask` 分支**：`hooks/index.ts:423-427` 的 `ctx.approval.decide({...})` 不带 `sessionId`/`sessionPath`，`decide` 内部按 `sessionOf(undefined)` 回落到当前查看会话（`approval/index.ts:718-725`）。这行本身是**既有**写法，但以前队友根本走不到 20 号钩子守卫（自建链里没有它），所以是**被本次改动放大成可达**：队友触发「钩子要求确认」时，卡落在用户此刻看的那条会话名下，档位与授权记账都记错会话；用户若看的是另一条会话，卡看不见，队友等到超时。

**P0-12-6 `risk:'exec'` 是否所有档位都弹卡**：不是。按 `decide` 的层序（`approval/index.ts:1203-1420`）：`auto-edit` 档会弹卡（该工具不是 `PATH_WRITE_TOOLS`，`verdict` 为 null，两条自动放行都不成立，1317-1368）；`full-access` 档**直接放行不弹卡**（`:1332`，这是该档的语义）；`auto-review` 档由判官裁决，判低风险就放行；`readonly` 档**直接拒**（`:1318-1327`，写/执行类一律拒绝）；无人值守（`someoneCanAnswer()` 为假）**直接按拒处理**（`:887-892`），不会挂 300 秒。所以「默认要人批」只对 auto-edit 与 reviewer=user 成立。

**P0-12-7 设置文案与旧配置**：一致。默认 `lookWithoutApproval:false`（`dock-browser/index.ts:98`），未设置时就是 `false` → `exec` → 每次过审批（`:211`、`:991`）；文案改成「关着的时候每次都要你点一下同意」与行为对得上。唯一不准的是「看（browser_dock_look）恒可用」：只读权限档与计划/探索模式里它会被整档拒（见问题 4）。

**P0-13-8 25 秒定时器的清理**：三条路清了两条半。工具关页签时清（`dock-browser/index.ts:739`）、插件停用时遍历清（`:1046-1049`）、收到 `Page.javascriptDialogClosed` 也清（`:411`）。**没清**的是用户自己在壳里关掉页签：这条没有事件回推，`states` 里也一直是旧条目（既有问题），所以 25 秒后定时器仍会调 `link.session(viewId)` 发一条 `Page.handleJavaScriptDialog`。不会崩：`createDockSession` 是纯工厂不抛（`core/dock-session.ts:40-44`），命令会被桌面侧拒掉并被 `.catch(() => {})` 吞掉（`:296-301`）；只是留下一条幽灵状态直到插件重启。切会话不影响，dock 视图不按会话分家。

**P0-13-9 「表面修了、实际卡死」**：判断成立，但程度比原文轻。`dialogHint()` 只拼在 snapshot（`:602`）与 navigate（`:757`）的成功结果前；click/type 这类动作在弹窗挂着时仍然吃满 25 秒超时，抛出来的错误里没有弹窗提示，而且文案是「桌面壳没有应答。侧栏窗口可能已关闭，或这一台视图已经不在了」（`host-stdio/index.ts:275-277`）——把模型往「视图没了、重开一张」的方向引。另外弹窗挂着时 snapshot 自己的 `Accessibility.getFullAXTree` 也会被压住，所以提示能不能露出来取决于「兜底定时器先于命令超时」这一下竞速。模型现在有 `dialog` 这个动作可调，但缺一条「任何 dock 结果/错误都带弹窗提示」的兜底，实际卡死只是缓解。

**P0-14-10 `shell:true` + 手写引号会不会被 cmd 解释成额外命令**：`quoteForCmd` 的规则是「含空白或 `"&|<>^()` 就整段加双引号，内部 `"` 换成 `\"`」（`core/shell-quote.ts:17-19`）。实测（复刻 Node `shell:true` 拼出的 `cmd /d /s /c "…"`）：`pkg with space`、`a&b`、`a^b`、`c|d` 都被当字面量传给程序，`&`/`|`/`^` 在引号内不生效；但 `%VAR%` 在引号内**照样展开**；参数的 `"` 用 `\"` 转义在 cmd 下**无效**——`x"&echo INJECTED-A` 会把 `echo INJECTED-A` 当成第二条命令执行。这是既有缺陷（`mcp.ts:907` 的 args 映射与 LSP `lsp/client.ts:235` 都一样），本次只是把同一份 `quoteForCmd` 也用到了可执行文件路径上（路径里不可能有 `"`，所以没有新增注入面）。建议：改用 cmd 的 `""` 转义并显式处理 `%`，或对参数里出现 `"`/`%` 直接拒绝并给一句人话。

**P0-14-11 cmd 内建命令是否回归**：是回归，但落点很窄。`resolveExecutable` 找不到就 `found:false`（`core/executable.ts:72`），`mcp.ts:906` 随即抛「命令没找到」；修复前是 `shell:true` 把原文交给 cmd 兜底，`command:"dir"` / `"echo"` 能跑。实测本机 `dir`、`echo` 都是 `found:false`。`.ps1` 不是新增回归：旧代码的候选表里同样没有 `.PS1` 兜底、命中了也是 `shell:false`，两版都起不来。设置页默认示例只有 `npx`，把内建命令配成 MCP server 属于想不开的用法，判为**可接受的收紧**，但建议在错误文案里加一句「cmd 内建命令（dir/echo/copy）不支持，请写成 cmd /c」。

**P0-14-12 `lsp/servers.ts` 缺 file 引号**：确认是既有问题、本次没碰（`git diff 752badb -- src/packages/lsp/` 为空）。LSP 把 `target.file` 直接交给 `spawn`（`lsp/client.ts:236-241`），`shell:true` 且路径含空格时会被 cmd 拆开——与新 `core/executable.ts:33-38` 注释里写的情况一致；新模块的 `spawnFile` 已解决，LSP 那边等合并时一起接。

## 三、发现的真问题（按严重度）

1. **PTC 绕过归属改写，沙箱按「用户正看着的会话」判** — `ptc/index.ts:262-271`、`:391-395`；`sandbox/index.ts:175-184`；`subagent/index.ts:534-546`。现象：队友调 `run_code` 时守卫入参是队友自己的 sessionId。触发：队友工牌不限工具（`toolsFor` 走 `ctx.tools.list()` 全量，`subagent:448-451`）且脚本里写盘/跑命令；用户同时把另一条会话切到完全访问档。后果：围栏整档被跳过，队友在工作区外的写不受沙箱约束。建议：把改写抽成一个共享函数（`ownerOf(sessionId)`），PTC 与循环都走它；或在 `guards` 服务层做一次「会话归属解析」钩子，而不是靠各调用点自觉。置信度：高（读码确定，无实测）。
2. **嵌套队友的父队友出队后，归属断在中间层** — `subagent/index.ts:499-509`、`:440`、`:1218`、`:104`（默认 maxDepth=1）。现象见问题 3。触发：`maxDepth=2` + 父队友是一次性或被挤出名单。后果：卡看不见、队友空等 300 秒；沙箱档回落成当前查看会话。建议：`Teammate` 里直接存一个 `ownerSessionId`（派活时算一次并固化），`ownerSession` 不再靠 Map 反查；出队时保留最后一位 owner 的映射。置信度：高（读码 + 时序推理）。
3. **hooks `ask` 卡不归属发起会话** — `hooks/index.ts:423-427`。现象：`ctx.approval.decide` 不收 `sessionId`/`sessionPath`。触发：队友（或后台会话）命中 hooks.json 的 `ask` 规则。后果：卡落到用户当前查看的会话，档位与授权记账错位；看不见时会挂到超时。建议：与 `subagent:605-606` 一样把 `input.sessionId` / `input.sessionPath` 传进去（`input` 里现成有）。置信度：高。
4. **`browser_dock_look` 在只读权限档与计划/探索模式下整档被拒** — `approval/index.ts:1318-1327`（写/执行类一律拒）、`session-core/modes.ts:97-99`（`readOnlyCommand` 对没有 command 的工具返回 false）、`:103-129`。现象：`risk:'exec'` 的工具在没有 `command` 参数时既不像读工具那样放行，也不像写工具那样弹卡，直接撞上「执行类一律拒 / 只跑只读命令」。触发：只读权限档、`/plan`、`/explore`。后果：模型仍然拿不到 ref，click/hover/type 三个动作在这三种档里依旧不可用——P0-12 只在「执行模式 + auto-edit/full-access」这一格修好了。建议：给 look 一类「只读但要看用户登录态」的工具单独一档风险（例如沿用 `read` 但在审批层按工具名强制弹卡），别用 `exec` 借道。置信度：高（读码确定）。
5. **弹窗提示不覆盖超时错误路径** — `dock-browser/index.ts:602`、`:757`（只有这两处拼 `dialogHint`）；`host-stdio/index.ts:275-277`（超时文案指向「视图不在了」）。现象：弹窗挂着时 click 超时，模型拿到的错误与弹窗无关。触发：页面 `confirm()`/`alert()` 挂着且模型先做的是动作而不是快照。后果：模型重试同一个动作、或去重开页签，用户侧看到的还是 25 秒一轮的卡顿。建议：`runAct` 的错误出口统一前置 `dialogHint(viewId)`，并把超时文案改成「可能被页面弹窗压住，先 snapshot 看有没有弹窗」。置信度：高（错误出口只有一处可改，读码确定）。
6. **`quoteForCmd` 用 `\"` 转义，cmd 不认** — `core/shell-quote.ts:17-19`，消费方 `mcp.ts:907`、`lsp/client.ts:235`。现象：参数里带 `"` 时拼出的命令行被提前闭引号，`&` 后的内容变成第二条命令（实测 `x"&echo INJECTED-A` 真的执行了 `echo`）。触发：走 `shell:true`（即命令解析到 `.cmd`/`.bat`，如 `npx`）+ 参数含双引号（例如给 MCP server 传一段 JSON）。后果：正确性直接坏掉（多数是拼坏参数），最坏是把参数尾巴当命令跑；写配置的人本来就能配任意 `command`，所以不算提权面。建议：按 cmd 规则改用 `""`，并对 `%` 做 `%%` 处理或直接拒绝可疑参数。置信度：高（机制已实测），影响面：中低（配置可信）。
7. **找不到命令不再交 cmd 兜底** — `core/executable.ts:72`、`mcp.ts:906`。现象：`command:"dir"`/`"echo"` 从「能跑」变成「命令没找到」。触发：把 cmd 内建命令写成 MCP server 的 command。后果：这类既有配置静默失效（好在报的是可读错误，不是超时）。建议：错误文案补一句内建命令的绕法。置信度：高（实测 `found:false`）。
