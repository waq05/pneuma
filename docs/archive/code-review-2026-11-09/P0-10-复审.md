## 一、结论：有条件可收（当前状态不建议直接合并）

**理由（按分量）：**

1. **方向对，且做对了大半**：三面确实共用了一份「事实」，三张结论表都还在，优先级写清楚了；12+ 条对照命令里没有任何一条从 `deny/forbidden` 变成 `allow`（不弹任何卡直接跑），`git push --force` 的拒绝理由现在会说明「审批面本会问人」。
2. **但违反了一条硬约束：放宽了现有 deny。** 地板原先对「内层脚本判不出」一律拒；现在改成递归判内层，内层「看着干净」就 defer。问题在于地板的递归只看灾难/硬地板/黑名单，**不看写目标**，而围栏的写目标识别只认命令行上的字面量。两头一夹，`bash -c "find / -delete"`、`cmd /c "for %f in (C:\Windows\*) do del %f"`、`powershell -Command "Start-Process cmd -ArgumentList '/c del C:\Windows\x'"` 这类命令从「地板硬拒」变成「审批 ask」；`ask` 在「完全访问」档会被自动放行（`src/packages/approval/index.ts:1332`，且该档下沙箱 `check` 直接返回 allowed，`src/packages/sandbox/index.ts` 的 `check` 首行），于是等价于**任何权限模式都能跑**——正是硬地板承诺要挡住的那一类。
3. 其余问题都是「提示不准」「探针自证」级别的，不阻塞，但应当同批修掉。

**收的条件（必须先做，否则建议只回退地板那一处）：**

- 地板的递归加一道 fail-closed：内层命令的 `effectiveVerb` 不在「能静态判清写目标」的白名单里（`rm/del/rmdir/cp/mv/set-content/…` 之外，尤其 `for`、`find`、`Start-Process`、`Invoke-Expression`/`iex`、`&`、`.`、管道末端）就仍然按「判不出」拒。宁可误拒，不可把判不清的脚本交给一张会被自动放行的卡。
- 补 3 条探针：`bash -c "find / -delete"`、`cmd /c "for %f in (C:\Windows\*) do del %f"`、`powershell -Command "Start-Process cmd ..."`，并把「最终结论」按 `full-access` 档也算一遍。
- 顺手修 `approvalHint` 的两处口径（见问题 3）。

如果主控坚持「零放宽」的字面口径：只回退 `src/packages/approval-floor/approval-floor.ts`（手术清单见第六节），其余四个文件可以收。

## 三、逐条回答

### 1. 有没有放宽安全边界？

放宽了，但形式是「地板 deny → 审批 ask」，不是「deny → allow」。见上表：`git push --force`、`rm -rf /`、`sudo rm -rf /`、`bash -c "rm -rf /"`、`powershell -EncodedCommand`、`.env` 读取这些真正危险/敏感的路径都还拒着（`.env` 靠地板自带的 denyGlobs，编码命令靠 `parseable:false`）。真正的口子在「内层脚本判不清、但地板也看不出问题」这一类：`find -delete`、`for` 循环、`Start-Process` 二层壳、管道末端 `Remove-Item`。原基线里它们统统被「内联脚本判不出」这条兜住；现在这条兜底被换成了「内层看着干净就放」，而下一个兜底（围栏）看不见这些形状。改法见结论里的 fail-closed 白名单。

### 2. 真的是「共享事实、各自结论」吗？

基本是，但边界不干净。

- 三张结论表都还在：`src/core/command-policy.ts` 的 `HARDLINE`/`DANGEROUS`/`READONLY_HEADS` 未改（`HARDLINE` 见 `src/core/command-policy.ts:248`）；`src/packages/sandbox/execpolicy.ts:53/130` 的 `FORBIDDEN_RULES`/`ALLOW_RULES` 原样保留；`src/packages/approval-floor/approval-floor.ts` 的 `POWER_HEADS`（`:419-427`）、`FORK_BOMB`（`:433`）、denyGlobs 判定都在。
- 档位也各自保留：allow/ask/deny、allow/prompt/forbidden、deny/defer 三套枚举互不替换。
- 但共享模块里混进了判定口径：`NETWORK_SUBCOMMANDS`（`src/core/command-intent.ts:258-280`，例如 `docker run`/`docker build` 算联网）、`FULL_WRITE_HEADS`/`COPY_HEADS`/`MOVE_HEADS`（`:128-140`，`cp` 只算最后一个词元）这些不是「事实」而是「口径」。这不算错，但注释里「只统一事实、不统一结论」（`:9-10`）说得太满；建议把那几个表标注为「三面共用的判定口径，改动等于同时改三面」。

### 3. `approvalHint` 会不会泄露信息、或让人误以为「开个开关就能跑」？

不会泄密，但有两处口径不准，会给出错误预期。

- 位置：`src/packages/sandbox/execpolicy.ts:207-212`，只在 `network-off` 分支追加（`:253`）。
- **泄露**：消息里只有「审批面会问/会放/会同拒」，没有规则内容、路径、密钥，也没有泄漏用户黑名单。可以接受。
- **误以为开开关就能跑**：对 `git push --force` 是准确的——打开网络开关后沙箱放行、审批卡照常弹。但它对所有网络拒都给同一句「要放行先打开网络开关」，而 `network-off` 在 `ASKABLE_RULES` 之外（`src/packages/sandbox/index.ts:130`），确实只能靠开关，这点没错。
- **口径不准（真问题）**：`approvalHint` 调的是 `classifyCommand(command)`，不传 `rules`（`src/packages/sandbox/execpolicy.ts:208`），也不看权限档。于是：用户已有 allow 前缀规则时，它会说「会弹卡问人」而实际不弹；`readonly` 档或无人值守子代理里，`ask` 根本不会变成卡（`src/packages/approval/index.ts:1318-1327` 直接拒），它会说「会弹卡问人」而实际是拒。建议：文案改成「审批面结论：需人工确认（是否弹卡取决于权限档与已授权规则）」，或把 `activeRules()` 与当前档传进来。
- **覆盖面**：`write-target` 拒绝（更常见的一类围栏）没有对应提示，`execpolicy.ts:267` 的理由没带审批面结论，和主控要求「围栏先拦时把理由说清」只做了一半。

### 4. 内联命令识别（`-Command` / `/c` / `-c` / `-EncodedCommand`）

- 地板现在能看见内层了：`src/core/command-intent.ts:334-360` 的 `inlineShellOf` 认 `-command/--command/-c//c//k/-encodedcommand/-enc`，`src/packages/approval-floor/approval-floor.ts:497-508` 拿到 `inline.command` 后递归走 `innerDenyReason`。实测 `bash -c "rm -rf /"`、`cmd /c "format C:"`、`powershell -Command "Remove-Item -Recurse -Force C:\Windows"` 仍被地板拒，且理由换成内层的（「删掉文件系统根目录」「格式化磁盘」），比原来那句「判不出」有用。
- 编码命令没有被「洗白」：`-EncodedCommand`/`-enc` 返回 `parseable:false`（`:310`、`:345`），地板在 `:502` 直接拒；`innerShellCommand` 对编码命令返回 `null`（`:368-370`），沙箱也不会把 base64 当明文再判一遍。实测 `cmd /c powershell -EncodedCommand …` 仍拒。这一条做对了。
- **截断误判为安全**：有一处。`inlineShellOf` 在「开关后面没有词元」时返回 `null`（`:344`），调用方把它当成「不是内联形态」，于是 `bash -c`、`cmd /c ""`、`powershell -EncodedCommand`（没给值）从基线的 deny 变成 ask。这几种其实跑不出东西，风险低，但语义上属于「判不出却当成没事」，建议返回一个 `parseable:false` 的占位而不是 `null`。
- **仍然看不见的形态（存量缺口，本次未修）**：POSIX 的组合短开关，例如 `bash -lc "rm -rf /"`、`sh -xec "..."`。`INLINE_FLAGS` 只认单独的 `-c`，`bash -lc` 整条落到审批面 ask；而 `HARDLINE` 是按命令位置匹配的，`rm -rf /` 藏在引号里也匹配不到。实测前后都是 ask，`full-access` 下会直接跑。建议把 POSIX 分支放宽成 `/^-[a-zA-Z]*c$/` 这类组合开关识别，或在 `classifyCommand` 之前也做一次内联展开。

### 5. 循环依赖

没有形成运行时环。

- `src/core/command-intent.ts:30` 是 `import type { CommandSegment }`，`tsconfig.json` 未开 `verbatimModuleSyntax`，`import type` 在编译期被整句删除。
- 运行时边只有一条方向：`command-policy → command-intent`（`src/core/command-policy.ts:21`，取 `commandIntent`）、`execpolicy → command-policy + command-intent`（`src/packages/sandbox/execpolicy.ts:23-31`）、`approval-floor → command-policy + command-intent`（`src/packages/approval-floor/approval-floor.ts:29-31`）。`command-intent` 运行时不 import 任何本项目模块（只有 node 内建没有），所以无环。
- `src/core/sandbox/execpolicy.ts` 只有一行 `export * from '../../packages/sandbox/execpolicy.js'`，是垫片，也不构成环。
- 提醒：`command-intent.ts` 里任何一处把 `import type` 改成值导入，就会立刻形成 `command-policy ↔ command-intent` 的运行时环（`commandIntent` 在模块顶层就会拿到半初始化的 `CommandSegment` 相关导出）。建议在那行加注释钉住原因。

### 6. 探针可信度

68 条里有 **30 条（44%）是同义反复**，另有若干预期是「照着实现写」的。

- `src/packages/sandbox/execpolicy.ts:32-34` 把 `innerShellCommand`/`isNetworkSegment`/`writeTargetsOf` 原样 re-export；探针 `scripts/command-intent-consistency-check.mjs:144/147/149` 拿 `ep.X(segment) === intent.X` 去比——同一个函数、同一份入参，永远为真。实测三个函数引用完全相等。这 10 条用例 × 3 条 = 30 条断言，无论实现怎么错都会 PASS。
- 探针没有「基线对照」，所以注释里「没有放宽任何一条灾难/越界/编码命令的 deny」（`:10`）只是手挑 8 条用例的结论，不代表全集；`find -delete`、`for` 循环、`Start-Process` 都不在用例里。
- 探针固定 `networkAccess:false`，从不跑网络开着的路径；也从不跑 `full-access` 档，所以「deny → ask」看起来无害，掩盖了上表最后 4 行的实际影响。
