# 测试入门（dsc 版）

> 给谁看：第一次给这个仓库写测试的人，以及被要求「补测试」的 AI 助手。
> 读完你应该能回答：测试为什么存在、测什么、怎么写、怎么验收、什么算好。
> 想直接看「我们这套体系长什么样」，翻 [testing-design.md](testing-design.md)；想看落地细节，翻 [testing-detailed-design.md](testing-detailed-design.md)。

## 1 测试的目的

先破一个误解：**测试不能证明代码是对的**，它只能证明「在这些输入下，行为符合预期」。

那它有什么用？三个具体的。

### 1.1 防回归

改 A 不要悄悄弄坏 B。仓库里现在有 264 个 spec 文件、2000 多条用例，另有一批留在 `scripts/` 的探针；每一条的抬头大多写着它防的是哪次事故。最典型的是 [session.int.spec.ts](../src/core/session/session.int.spec.ts)：0.6.46 版本发生过「同一 callId 两条工具结果 → DeepSeek 网关返回 400 → 这个会话之后每次请求都被拒」，修完之后把那次的输入原样固化成断言。以后再改会话加载逻辑，这条测试替你盯着。

### 1.2 固化决策

把「我们商量好要这样」变成机器每次都能检查的东西。

「压缩后必须保留最近 3 轮」这句话写在文档里会过期；写成 `expect(compacted.length).toBe(3)` 就不会。

### 1.3 降低验证成本

手工点一遍要 10 分钟，跑一遍测试要 2 秒。改一行代码能跑二十遍，人做不到。

### 1.4 测试不负责什么

- 不负责证明「没有 bug」——证明不了。
- 不负责代替代码评审——评审看的是设计和可读性。
- 不负责代替用户验收——用户看的是「能不能用」，测试看的是「行为有没有变」。

指望测试证明「产品能用」是错位的。那是真模型冒烟（`tests/live/`）和真入口测试（`tests/cli/`）的工作。

## 2 测什么

### 2.1 按「坏起来最疼」排序

| 类型 | 例子（本仓库的代码） |
| --- | --- |
| 纯函数与边界 | `clamp`、`shell-quote`、`token-estimate`、`todo-reminder` 的轮次计算 |
| 错误路径 | 模型超时、SSE 半截断开、配置文件损坏、沙箱拒绝 |
| 状态迁移 | 会话：新建 → 跑回合 → 压缩 → 恢复 |
| 时序与并发 | 两条请求同时写同一个会话、子代理与主代理争用 |
| 外部契约 | 模型返回的形状、插件接口、界面与内核之间传的数据结构 |

### 2.2 不测什么

**别测实现细节。** 测「压缩后保留了几轮」，不测「压缩函数内部调了几次 `slice`」。实现一改，后者全红。

**别测私有方法。** 要测就说明它该是公开的。

**别用源码文本断言。** 仓库里现在有大量这种：

```ts
// ✗ 反例：读源码字符串，假装在测行为
check('勾选框是画的', read(TODO_VIEW).includes('tc-todo-box'))
```

它有两个毛病：
- 改个类名就**假红**（代码没坏，测试叫了）；
- 改坏渲染逻辑但类名还在就**假绿**（代码坏了，测试没叫）。

**别对一个测试写多个不相关断言。** 坏了要先猜是哪个断言红的。

### 2.3 三层，各管一段

| 层 | 测什么 | 速度 | 数量占比 | 本仓库现状（2026-11-14） |
| --- | --- | --- | --- | --- |
| **单元** | 一个函数/一个模块，不碰网络和磁盘 | 毫秒 | 60–70% | 插件包 119 个 `.spec.ts` + 内核 16 个模块，合计 2000 多条，跑 `pnpm test` |
| **集成** | 几个模块 + 假外部（假模型），起真内核 | 秒–分钟 | 20–30% | 79 个 `.int.spec.ts`，约 1200 条，跑 `pnpm run test:int` |
| **端到端** | 从真入口走完整链路 | 分钟 | 5–10% | 还没建（P3 的 e2e project） |

这叫**测试金字塔**。这个仓库花了 2026-11 半个月把它从「缺角」补成了「三层都有」：
单元层最厚，集成层第二，端到端还空着。空着不丢人，写一条假的端到端比空着更糟。

## 3 怎么做

### 3.1 一条测试的三个部分

准备（Arrange）、执行（Act）、断言（Assert），缺一不可。

```ts
test('距上次写清单过了 7 轮，返回 7', () => {
  // 准备：1 次 todo_write + 7 轮对话
  const history = [userMsg('开始'), todoWriteMsg(), ...rounds(7)]

  // 执行
  const actual = countRoundsSinceLastTodoWrite(history)

  // 断言：具体到一个值
  expect(actual).toBe(7)
})
```

### 3.2 命名说清「什么条件下、期望什么」

| 差 | 好 |
| --- | --- |
| `test('test1')` | `test('距上次写清单过的轮数，不算工具结果消息')` |
| `test('压缩正常')` | `test('压缩后保留最近 3 轮，更早的转成摘要')` |

名字是失败报告里唯一会被人读到的那句话，值得多花十秒。

### 3.3 五条硬要求

| 要求 | 说明 | 反例 |
| --- | --- | --- |
| 一个测试只验一件事 | 坏了能立刻知道坏在哪 | 一个 test 里断言 8 个不相关的东西 |
| 断言要具体 | 验值，不验「有东西」 | `expect(x).toBeTruthy()` |
| 不依赖执行顺序 | 单独跑、倒着跑、并行跑都过 | A 建的临时文件，B 去读 |
| 不依赖外部世界 | 不联网、不读真实 `~/.dsc` | 直接写用户主目录 |
| 失败信息能定位 | 报错说清「期望 X，实际 Y」 | `expect(false).toBe(true)` |

### 3.4 隔离：临时 HOME

本仓库的硬规矩：**任何会在用户目录写文件的测试，必须走临时 HOME**。

```ts
const home = mkdtempSync(join(tmpdir(), 'dsc-xxx-'))
process.env.HOME = home
process.env.USERPROFILE = home   // Windows 认这个
```

理由不是洁癖：测试往真实 `~/.dsc` 写，会污染用户正在用的会话，而且并行跑会互相踩。

### 3.5 假外部：只 mock 贵的和不确定的

DSH 的测试政策里有一条值得照抄：**只 mock 昂贵的或不确定的边界（模型、网络、时钟），下游全部用真的**。

```ts
// 好：模型是假的，内核、会话、工具注册表全是真的
const site = await fakeLLM({ turns: [...], baseUrl: 'http://127.0.0.1:PORT' })
const ctx = await bootKernel({ provider: site.baseUrl })
```

自己造一个「假内核」来测「假插件」，只能证明「管子通了」，证明不了产品行为。

## 4 怎么验收

### 4.1 最关键的一步：反向验证

**写完测试，故意把代码改坏，看它红不红。**

红了，说明这条测试有效；还绿着，说明写了个摆设。

具体操作四步：

1. 改坏一行（把 `>=` 改成 `>`、删一个赋值、换一个分支）。
2. 跑测试 → **必须红**。
3. 改回来 → **必须绿**。
4. 提交信息里写一句：「反向验证：改了边界条件，测试变红」。

不做这一步，你会得到一堆「永远绿」的测试：不拦任何东西，只增加维护成本。这是 AI 写测试最容易翻车的地方——一天能写两百条永远绿的测试。

这条对齐 DSH 的明文规矩：「A guard only guards if the regression fails it」（守卫只有在回归能让它失败时才算守卫）。

### 4.2 交付前的七项检查

| 检查 | 做法 | 期望 |
| --- | --- | --- |
| 反向验证 | 改坏代码 | 红 |
| 单独跑 | 只跑这一条 | 绿 |
| 全量跑 | 跑整个套件 | 绿 |
| 重复跑 | 连跑 3 次 | 3 次都绿（不抖） |
| 乱序跑 | 打乱顺序 | 绿（无依赖） |
| 耗时 | 看单条用时 | 在层级预算内（单元 < 100ms） |
| 失败可读 | 故意让它失败 | 报错能看出期望与实际 |

### 4.3 「通过」这个词怎么用

**「通过」只有在贴出命令和退出码时才有意义。**

| 说法 | 价值 |
| --- | --- |
| 「全部通过」 | 什么都不是 |
| 「测试都跑过了」 | 什么都不是 |
| 「`pnpm test` 退出码 0，243 条用例全绿」 | 可核验 |
| 「跑了 240 条，3 条失败，失败原因分别是……」 | 可核验且诚实 |

## 5 什么算好

### 5.1 单条测试的标准（业界叫 FIRST）

| 字母 | 含义 | 人话 |
| --- | --- | --- |
| **F**ast | 快 | 单元测试毫秒级；等不起的测试没人跑 |
| **I**ndependent | 独立 | 不依赖别的测试留下的状态 |
| **R**epeatable | 可重复 | 同一份代码，跑一百次结果一样 |
| **S**elf-validating | 自校验 | 通过与否由断言决定，不靠人看输出 |
| **T**imely | 及时 | 和代码一起写，不是半年后补 |

### 5.2 一套体系的标准

| 指标 | 及格线 | 本仓库目标 |
| --- | --- | --- |
| 金字塔比例 | 单元占多数 | 单元 60%、集成 30%、端到端 10% |
| 覆盖率 | 核心模块有数字、不倒退 | 只降不升基线（**不设 100%**） |
| Flake 率 | < 1%（一百次里抖不到一次） | 重试 + 串行组 + 超时治理 |
| 门禁分层 | 快的进 PR，慢的进夜跑 | unit/ui 进 PR，集成/e2e 夜跑 |
| 真实性 | 至少一层碰真东西（真模型/真入口） | 5 条 live + 8 条 cli |

### 5.3 三个最常见的错误标准

**「测试数量多就是好」**——200 条永远绿的测试，不如 20 条会红的。

**「覆盖率 100% 就是好」**——100% 只说明每行都被执行过，不说明每行都被验过。本仓库如果硬上 100%，能写出满覆盖但一个 bug 都抓不住的测试。

**「我这跑过了」**——本机绿不等于干净检出绿。[verify.yml](../.github/workflows/verify.yml) 第 5-6 行记着这个教训：2026-10-28 一天红了两次，全是「本地绿、CI 红」，原因是本机有未跟踪的文件兜着。

## 6 本仓库的具体规矩

| 规矩 | 出处与理由 |
| --- | --- |
| 判定只看退出码 | [_check-runner.mjs](../scripts/_check-runner.mjs)。探针各自打印「N PASS」写法不统一，拿它当判据迟早误判 |
| 新探针按命名自动进门禁 | [check-core.mjs](../scripts/check-core.mjs)。手挂清单永远追不上 |
| 临时 HOME | 见 §3.4 |
| Vitest 只 import `src/`，探针只 import `lib/` | 两个平面混用会产生两份模块实例，`command-runner` 的模块级 Map 分家 = 沙箱 fail-open |
| 测试文件后缀决定层级 | `.spec.ts` / `.int.spec.ts` / `.spec.tsx` / `.e2e.ts` / `.snapshot.ts` / `.bench.ts` / `.live.e2e.ts` / `.cli.e2e.ts` |

## 7 常见误区对照表

| 误区 | 事实 |
| --- | --- |
| 测试是写完代码再补的 | 好测试是写代码时写的，补的测试通常只覆盖「我知道它做什么」 |
| 覆盖率越高越安全 | 覆盖率只证明执行过，不证明验过 |
| Mock 越多越隔离 | 全部 mock 的测试只证明「壳子能跑」 |
| 测试失败就改测试 | 先确认是代码错还是测试错；改测试前必须能解释为什么 |
| 端到端能测就不写单元 | 端到端慢且定位难；单元测边界，端到端测接缝 |
| 测试数量是 KPI | 会红的测试才是资产，不会红的测试是负债 |
